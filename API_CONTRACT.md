# Current backend and Settings contracts

Canonical types: `shared/contracts.ts`. This document describes the local API and labeled web mocks. Automatic submission uses separately saved, default-off future author/action consent, not implementation approval or an AI verdict. Authentication, tool grants and live provider readiness remain separate. See [execution guide](docs/execution-modes.md) and [automatic submission](docs/automatic-submission.md).

There is one supported product: restricted **Isolated harnesses** with Main/Additional, independent skill-owned **Docker**, and confirmed full-native-inheritance **Dangerous**. No historical execution option is supported. Archived results and intent remain readable, without migration, permission inference or rerunning. Backend evidence and exact checks: [execution-modes.md](docs/execution-modes.md). Security/support: [EXECUTION_BOUNDARY.md](EXECUTION_BOUNDARY.md), [isolated-capabilities.md](docs/isolated-capabilities.md), [known profiles](docs/known-mcp-profiles.md).

## Settings contracts

All paths start with `/api`. JSON errors are `ApiError`; malformed requests use 400, unavailable/incompatible setup uses 409. Existing loopback host/origin checks apply. GET/SSE returns cached state, never discovers configuration, resolves credentials, probes providers, starts setup or saves.

- `GET /state -> AppState`. `settings` no longer exposes the internal `harness` persistence object, skill bytes, source catalog, managed ids or consent records. `health` contains only `github`, `githubUser`, `lastPollAt`, `pollError`, `demo`. Fixed-pair `claude`, `codex`, `skill` health fields are retired. Use execution controls' saved provenance/diagnostics, not a standalone raw Tool health/Diagnostics panel.
- `PATCH /settings`, body `SettingsUpdate -> AppState`: repository, partial independent `automation`, poll interval and `maxConcurrentReviews` only. Defaults are all automation off, concurrency 1 (integer 1-8), poll interval 300 seconds. Auto-review never enables its polling switch. Empty repository forces automation off. Existing baseline, per-PR overrides, dedup, restart and submission behavior is unchanged. Execution/integration settings use their dedicated explicit actions, never unrelated Settings saves.
- `GET /settings/harness -> HarnessStatus`: required `selection:HarnessSelection|null`, `archivedSelection:{version?,harness,workflow,reviewer?}|null`, `requiresSave:boolean`, `reviewer:{skillPath,model}`, `mode:ExecutionMode|null`, `effective:HarnessSelection|null`, `options`, `setup:DockerSetupStatus`, `capabilities:[{id,policy}]`, `diagnostics:string[]`, `evidence:"unverified"|"synthetic_preflight"`. No `sources` or `supportedSources`. `effective` describes local executable compatibility, not authentication or connection success.
- Fresh unsaved intent is `{version:2,workflow:"dangerous",harness:"claude",reviewer:{skillPath,model}}`. Canonical `executionModes` and the visible/keyboard selector order are Dangerous, Isolated Harnesses, Docker. Existing explicit valid selections are preserved; unknown/archived state never becomes Dangerous intent. Selecting/defaulting a mode neither executes nor authorizes tools, and Isolated/Docker failures never fall back to Dangerous. Path/model come from backend defaults; model is normally null. No native files are captured on startup or GET. `requiresSave:true,effective:null` instructs an explicit Save before work. Save errors leave saved intent unchanged. Archived unsupported choices return `selection:null,archivedSelection,mode:null,effective:null,requiresSave:true`; show a short inline re-save action, not a historical mode switch or source editor. Existing v3 intent without `restricted-native-1` also requires re-save; absent fields never manufacture policy.
- `PATCH /settings/harness`, body `HarnessSelectionUpdate -> HarnessStatus`. Exactly the current discriminated selections below, plus `confirmation` only for Dangerous. `sourceId` is rejected even when null. No versionless, `legacy`, `configured`, or v2 `separated` body. Invalid shape is 400 `invalid_harness`; missing/nonportable skill/native configuration is 409 `skill_incompatible` without changing settings. Review-only skill requirements can be saved with `effective:null` and useful diagnostics; focused questions do not invoke the full review skill.

### Isolated harnesses v3: exact Fable handoff

```json
{
  "version": 3,
  "workflow": "separated",
  "harness": "pi",
  "reviewer": {
    "skillPath": "/absolute/skills/audit/REVIEW.md",
    "model": "openai-codex/gpt-6-astra"
  },
  "additional": [
    { "id": "reviewer-1", "harness": "codex", "model": "model-one" },
    { "id": "reviewer-2", "harness": "codex", "model": "model-two" }
  ]
}
```

Use `HarnessSelectionUpdate`, `IsolatedHarnessSelection`, `HarnessModelEntry`, `CapturedHarnessEntry`, `IsolatedRolesSnapshot`. Top-level `harness` is **Main harness**, `reviewer.model` is **Main model**, `reviewer.skillPath` is the shared review entry. Main id is `main`. There is no extra synthesis model or hidden reviewer. Additional is required, ordered, 0-8 entries, exactly `{id,harness,model}`. Stable client row ids match `[a-zA-Z0-9][a-zA-Z0-9_-]{0,63}`, unique and never `main`. All three harnesses work in every role; identical harness/model pairs remain distinct by id. Never key or deduplicate by harness/model.

Every model is null or a nonempty id matching `[a-zA-Z0-9][a-zA-Z0-9._/:+-]{0,199}`. Null means **Native default, resolved on Save**, independently for each entry. Supported defaults: Claude native model else `claude-fable-5`; Codex native model else `gpt-6-astra`; Pi native provider/model else `openai-codex/gpt-6-astra`. Save reads supported ordinary native configuration, instructions, preferences and effort, not credentials, model catalogs or providers. Selected model/profile restrictions take precedence. Responses contain resolved models. Pi restricted execution supports only its own documented openai-codex auth profile. No new effort UI is requested.

Save freezes the exact absolute Markdown entry filename, containing directory and bounded UTF-8 resources, plus the trusted native library and each role's `restricted-native-1` policy. `SkillSnapshot.files` reuses `CapturedResource`: logical `sourcePath`, target, content and executable bit, plus optional `resolvedSourcePath` and `sourceDigest` for explicitly trusted file resolution. Text retains absent/`utf8` encoding. Only Docker may capture recognized non-executable WOFF2/PNG skill companions with `encoding:"base64",mediaType:"font/woff2"|"image/png"`; these are opaque asset bytes, never instruction text. Isolated/Dangerous/local-MCP acceptance stays text-only. The latter binds the terminal path and ordered link identities; an identical-byte retarget changes the skill/disclosure identity. Only the selected entry's exact Home Manager backup siblings are excluded, never required dependencies. [Supported trusted source scope](docs/trusted-sources.md) leaves other resource links strict. Re-save explicitly to adopt changed bytes or source identity. The app sequentially invokes Additional reviewers with the same rubric/pinned PR, then Main performs full review, verifies evidence and synthesizes **one editable draft**. Main alone still performs a full review. App orchestration overrides nested reviewer/model instructions, not other unsupported requirements. Recognizable required shell/scripts/hooks/plugins/arbitrary MCP fail actionably; inventory is best effort, not a universal skill parser. Isolated is restricted native tools, not OS/process containment.

Immutable `reviewer.skillExecution` is `{version:3,mode:"separated",harness,skill,roles:{main,additional},policy}`. Each role captures id, role, harness, resolved model, instructions, optional low/medium/high effort and policy. Top-level reviewer model/instructions mirror Main; dispatch uses each active role's own policy. Revisions capture current explicit execution plus the original draft's PR snapshot and produce proposals without overwriting edits. Queued jobs retain captures. Ask AI is focused **Main-only**, never skill invocation or Additional fan-out. Supported follow-ups/retries retain the parent capture, not current Settings.

`ReviewRun.progress.entries?:HarnessEntryEvidence[]` is immutable history in execution order: Additional then Main. Each entry has id/role/harness/model, pending/running/completed/failed/interrupted/skipped, actual nullable timestamps, validated `result:ReviewResult|null`, bounded `error:string|null`. Result limit is 200,000 UTF-8 bytes; error limit is 4,000 characters. No truncation or partial result counts as success. Additional failure is retained, supplied to Main and disclosed in private final rationale. Main failure creates no successful draft. Cancel/shutdown skips unstarted entries and interrupts active work. Job concurrency/per-PR serialization remains unchanged. Display captured ids and models, never infer work from a role's presence on a question or current Settings.

### Docker and Dangerous

Use `NativeHarnessSelection`: `{version:2,harness:"claude"|"codex"|"pi",workflow:"docker"|"dangerous",reviewer:{skillPath,model}}`. No Additional list. Selected skill/native orchestration, independent primary model and preserved supported resources remain separate from Isolated's app-owned roles.

- Dangerous requires fresh exact `dangerousConfirmation` on **every** explicit save, including harness changes: `I understand this harness can write host files and publish directly without the app preview`. Missing/wrong confirmation is 400 `dangerous_confirmation_required`. Cancel sends nothing. Show the selected harness, full native tools/config/auth, host writes and publishing outside app preview. App gateway permissions do not restrict Dangerous. Captured `hostExecution:{version:1,harness,confirmedAt}` records backend-validated consent. Native config/auth remain external and mutable; app capture is not a restriction or complete freeze of host behavior.
- Docker Save can return `effective:null` until separate inspection, approval and setup. Save captures the skill and supported native defaults only; it never approves capabilities or sets up a runtime.
- `POST /settings/execution/inspect`, body `DockerInspectRequest:{harness,localConnections?:DockerLocalMcpRequest[],exclusions?:string[],libraryLeaves?:string[]}` -> `DockerCapabilityDisclosure` (version 1, profile `container-native-1`). Requires the already saved matching Docker harness/model/path with unchanged skill bytes. `localConnections` (default none, at most eight unique discovered ids) reuses `NativeMcpImportRequest` plus explicit `enabled` and `allowedTools` for discovered **stdio** entries only; the shared known-profile registry is unchanged and a profile is not authorization. Inspection reads trusted local configuration/resource bytes and file metadata; it starts no process, reads no credential contents, never calls host Load/Test for stdio, installs nothing and approves nothing. Invalid shape is 400 `invalid_docker_inspection`; unsaved/mismatched selection, changed skill bytes, unsupported stdio adapters (only discovered `node`/`/usr/local/bin/node` with one absolute `.mjs` entry, no env/auth/helpers/extra args) or unsupported configuration are 409 `docker_inspection_failed` without changing saved intent. The returned `digest` is the exact disclosure identity: render it, never compute or modify it. Render skill/model/path/digest, `resources` (source, container target, digest, executable bit, optional `resolvedSourcePath` and `sourceDigest` for explicitly trusted file resolution, decoded size/encoding/media type for opaque assets, no content), every `customizations` entry (content-bound id, harness, `hooks|extensions|skill-code|shell-prefix`, source, digest and its arbitrary-container-code `capabilities`), every `authentication` entry (own source, `present|missing|not_checked`, `supported_reference`, `tested:false`, `temporary-container-access-token`, `all-container-code`, `refresh:false`, never relabeled authenticated/Connected), each `localConnections` entry (request, native identity, profile/profile digest, source digest, target, `container-stdio`, `inventory:not_tested`, `connected:false`), `boundary`, `requirements` and `evidence:"local_configuration"`. The pending preview is memory-only on the backend and cleared by Settings updates and restart; GET/SSE never inspect or refresh it.
- `POST /settings/execution/setup`, body `DockerSetupRequest:{harness,confirmation:dockerSetupConfirmation,approval?:DockerCapabilityApproval}`. `approval` is `{digest,customizations,credentialExposures,exclusions?:string[],libraryLeaves?:string[],confirmation:dockerApprovalConfirmation}` and must name the exact pending digest, every disclosed customization id and every disclosed credential exposure harness, no more and no fewer; missing, partial, extra, duplicate or changed choices, an old request without approval, or source/config drift since inspection return 409 `docker_setup_failed` before any installer action. Exact constants: `Set up the app-owned Docker runtime and read my installed skill and supported harness configuration` and `I approve these exact container capabilities and temporary model credential exposures`. Approval is collected from explicit unchecked per-item choices for customizations, credential exposures and shown local stdio choices, then the separate host-effects consent (`setup.message`: disclosed resources, pinned downloads, credential-free installer container/network, app-owned cache, Docker policy/runtime preflight). Never synthesize approval from defaults, discovered or native enablement, saved intent or old setup status; cancel sends nothing. It never installs Docker Desktop, selects a mode, reads model credentials, logs in, refreshes auth, calls inference/providers or enables automation. Unsupported configuration fails rather than stripping it. The source-bound Docker-only exclusion flow below may omit the exact approved UI-only items, official Slack activation flag or named Google Workspace skill projection without changing native files. Optional external installed skill leaves without per-alias read consent are skipped before content enumeration and disclosed under `sourceHandling`; the selected review entry, other external links and unsupported customizations remain required or refused. Docker has no host fallback.
- Setup response is `HarnessStatus` or 409 `docker_setup_failed`, with cached `setup.status:not_started|running|ready|failed`, harness and message; one setup at a time, explicit retry after re-inspection. Successful setup freezes the approved skill, portable projection, local grants and consent into the managed artifact. Cached runtime for another model/path/disclosure is not ready for this selection. A cached `ready` setup is readiness only, never selection, authentication or Connected.
- `GET /settings/execution -> ExecutionStatus` remains cached (`disabled|configured|unavailable`, message, nullable captured Docker snapshot and optional `lastApprovedDocker: DockerBoundarySnapshot`). Prior approval is a read-only same-harness projection only when the managed artifact's loaded digest matches the recorded source digest, even if changed saved inputs make `snapshot` null. It is not readiness, inspection, recapture or new consent. Unverifiable historical broker/runtime drift supplies no prior approval; the guided flow keeps its choices unchecked. `ExecutionSnapshot.docker?:DockerBoundarySnapshot` carries `{profile:"container-native-1",disclosure,approval}`; a cached artifact without it is `unavailable` with a message that it predates explicit approval. `disabled` means no Docker boundary for Isolated/Dangerous, not a disabled review. `POST /settings/execution/check {}` performs explicit credential-free Docker preflight only; success remains configured with synthetic-preflight evidence, failure is 409. Present this inline with Docker, never as raw global Diagnostics.
- Internal managed Docker artifacts and v2 control/broker pins remain app-owned and are not authoring APIs. Supported captured Docker jobs require their exact artifacts plus the `container-native-1` marker whose approval digest matches its disclosure. Archived v1, imported/versionless or marker-less captures cannot execute, retry or continue. Exact support matrix, enforcement and evidence: [docs/docker-boundaries.md](docs/docker-boundaries.md).

### Source-bound Docker exclusions and handling

`POST /settings/execution/exclusions {}` -> `{exclusions:DockerExclusion[],nativeSettingsUnchanged:true}` requires saved Docker intent. It reads bounded native settings and declared `.claude/skills/synced` library metadata. A recognized Google Workspace candidate additionally reads its nine bounded UTF-8 resources and sibling manifest to bind exact content, links and layout. It never executes captured code or a hook/status command, reads credentials, approves an item or changes native configuration. GET/startup/Save do not call it. Candidates are narrowly recognized Herdr `SessionStart` commands, command-type status lines, the exact official Slack activation flag and the named Google Workspace skill shape, not a general hook/plugin/skill selector. `DockerExclusion.kind` is `herdr-session-start|status-line|slack-plugin|google-workspace-skill`. The Slack candidate requires `enabledPlugins` to contain exactly `{"slack@claude-plugins-official":true}`; false, differently typed or additional entries produce no Slack candidate and remain unsupported at projection. Its pointer is `/enabledPlugins/slack@claude-plugins-official`, definition `true`, and item digest is SHA256 of `true`; the whole source/link/content identity also binds it. A candidate carries `id,source,sourceDigest,itemDigest,kind,pointer,definition,rationale,effect,nativeSettingsUnchanged:true`. Show the exact definition, identity, omitted Docker behavior and native-settings-unchanged disclosure before choosing it.

A `google-workspace-skill` candidate uses its sibling `manifest.json` as `source`, `/skills/<index>` as `pointer`, and a `definition` containing the one exact named skill entry, matching skill-only pending claims and bounded resource/layout identities, not script bodies. The recognized leaf is exactly `.claude/skills/synced/<bucket>/google-workspace` with `SKILL.md`, four `references/{charts,docs,sheets,slides}.md` and four `scripts/{docs_index,render_export,sheets_helper,slides_helper}.py` files. Additional/different files or unsupported manifest entries cannot inherit the selection. Whole manifest bytes, all nine file bytes/modes/resolved identities and leaf layout bind `sourceDigest`; `itemDigest` binds the shown definition. Explicit selection removes those nine resources before executable classification and container materialization and removes only that skill entry and exact `/google-workspace` pending-claim entries from the runtime manifest. All other JSON values are retained, with `inputDigest` binding the original manifest bytes. A `library-layout` handling record describes the omission; no native file is changed. Alias recapture of an excluded file, forged definition/pointer/identity or an exclusion outside the selected harness capture fails closed. No selection means the skill remains included and still requires ordinary code approval. Non-Docker projection is unchanged.

Pass explicit candidate ids in Inspect's `exclusions` (default empty, at most 32 unique digest ids). The backend rereads their exact config/item identities; changed, missing or additional unsupported items fail closed. The disclosure includes selected `exclusions` and `sourceHandling:DockerSourceHandling[]`: `kind` is `finder-metadata|presentation|host-project-trust|library-layout`, with logical source, digest, effect and `nativeSettingsUnchanged:true`. Resource `inputDigest` binds pre-projection settings bytes independently of transformed runtime content; existing resolution identities remain. Finder `.DS_Store`, inert theme/tui fields and host-only Codex project trust are disclosed non-runtime inputs, not arbitrary-code grants. Logical linked-library layout and trusted instruction closure retain bounded identity/drift checks.

Setup approval must echo **every selected exclusion id exactly**, alongside existing customization/exposure choices. Absent `exclusions` means empty, never implicit consent. Changing candidates/selection invalidates the preview and requires new Inspect and unchecked per-item approval before separate host-effects consent. Source edits are revalidated before setup; historical captures remain immutable. The original pre-exclusion UI cannot approve nonempty exclusions and therefore fails closed. Explicitly selected `slack-plugin` omission removes only that singleton activation map from the Docker projection; source/item/pointer drift or extra plugins fail closed. It does not modify native configuration, execute a plugin, approve arbitrary code, expose credentials or grant a broker read. Docker loses the official plugin's native MCP activation, six skills and five commands; separately captured instruction-only `slack-axi` and explicitly granted authenticated broker reads remain, without CLI or whole-plugin parity. The installed-leaf read-consent flow below is separate from executable approval and plugin permissions. The only binary exceptions are recognized non-executable WOFF2/PNG data in Docker skill `assets/` companions. Their `CapturedResource` explicitly carries `encoding:"base64",mediaType:"font/woff2"|"image/png"`; the disclosure resource carries those fields plus decoded `bytes` and a SHA-256 `digest` of the exact original bytes, not the base64 text. Render the MIME type/opaque-asset label, size, path, mode and digest, not base64 as instructions or an executable grant. Do not automatically render/decode a PNG preview. Text defaults remain unchanged; unknown/noncanonical encodings fail closed. Configurations/instructions and explicitly selected external leaves remain UTF-8-only. Other binary formats, archives, executables and local-MCP binary resources remain unsupported.

Capture recognizes the WOFF2 signature and bounded fixed header with supported single-font flavor and declared length/table/compressed-data fields. PNG recognition checks its signature, first 13-byte IHDR with standard dimensions/depth/color/methods and final IEND envelope. Both require a non-executable skill asset path and preserve exact bytes through frozen JSON and container materialization. These are format identification checks, not rendering, decompression or complete chunk/CRC/image/font validation. Docker has fixed 100-source/2000-entry, 2 MB per-file, 8 MB aggregate decoded, 16 MB serialized resources, 32 MB workflow, 20 MB initialization-frame and 24 MB input-queue caps (decimal bytes). Encoding does not bypass them; escaping/base64 expansion counts against serialized caps. Other modes/local-MCP remain at 2 MB, and business HTTP/provider/message limits are unchanged. Mode, byte, encoding or source changes invalidate stale approval. Host materialization refuses encoded assets, and model/requirement scanners do not interpret them as text. See [source limits and actual versus synthetic evidence](docs/trusted-sources.md).

`POST /settings/execution/library-leaf`, body `DockerLibraryLeafRequest:{source:string}` -> `DockerLibraryLeaf`, requires a saved current Docker selection. This is an explicit metadata-only observation of one direct installed skill child under the saved harnesses' declared native roots, not arbitrary path authoring. It resolves the terminal directory, ordered link identity and contained regular `SKILL.md`, without reading resource content or enumerating companions. Invalid body/extra fields are 400 `invalid_library_leaf`; unsupported path, escaping entry, changed identity or unsaved selection is 409 `docker_library_leaf_failed`. GET is 404. No automatic discovery/selection on Save/startup or GET.

The response reuses `TrustedLibraryLeaf:{source,resolvedSourcePath,sourceDigest}` and adds `id,limits:{entries:2000,decodedBytes:2000000,encoding:"utf8"},effect,nativeSettingsUnchanged:true`. Render the exact logical and terminal paths, ordered-link digest, independent bounded read effects and an unchecked **Read and freeze this installed leaf** choice before Inspect. Discovery alone grants no content reads. Inspect accepts only selected server-observed ids in `libraryLeaves` (default empty, maximum eight distinct ids), never caller-supplied paths/digests. Candidates are transient and cleared on Save/restart; re-discover after either. The backend revalidates each identity before reading and before setup, forbids external descendants and binds content/layout/mode drift to normal approval. A matching terminal through a different logical alias needs its own explicit choice. An unselected optional external directory directly under a declared native skills root is omitted before target content enumeration/reads, with its logical source and link identity recorded as `sourceHandling.kind:"library-layout"`. This applies even without metadata observation; omission never requires consenting to read it. It does not omit the selected review entry, ordinary bounded native/Nix libraries, external files, nested escapes or parent-root links.

Inspect returns selected `libraryLeaves:DockerLibraryLeaf[]` in the disclosure. Setup approval must echo every exact selected id in `approval.libraryLeaves`; missing/extra/stale choices fail 409 before host effects. Read selection is not executable-resource approval or setup consent. Successful artifacts retain immutable bytes and exact disclosure, not reusable blanket trust. The UI provides this separate read-choice/disclosure step, clears/stales previews when choices change and preserves distinct executable and host-effects gates. Optional external leaves are visibly described as omitted unless selected; required or otherwise unsupported resources still fail rather than being silently removed. Real installed and synthetic fixture outcomes remain separate in [trusted-source evidence](docs/trusted-sources.md).

## Precise review job controls

`PullRequest.reviewJobs?:ReviewJob[]` projects each active full-review or AI-revision job plus the latest stopped-job outcome in both Inbox state and PR detail. Each entry is `{jobId,runId,headSha,kind,status,cancellation}`. Older fixture/client absence exposes no action. `RunStatus` adds `unqueued` and `cancelled`; immutable `ReviewRun.cancellation?:ReviewCancellation|null` records `{status:"pending"|"confirmed"|"unconfirmed",requestedAt,finishedAt,message}`. Unconfirmed is not completed shutdown. GET/SSE only reads these records.

- `POST /api/prs/:id/jobs/:jobId/unqueue`, body `ReviewJobAction:{runId,headSha}` -> 200 `PullRequestDetail`. Exact queued identity only, synchronously removed from dispatch with history retained. If dispatch started, return 409 `review_job_conflict` describing the actual state, never switch to running cancellation.
- `POST /api/prs/:id/jobs/:jobId/cancel`, body `ReviewJobAction:{runId,headSha,confirmation:cancelReviewConfirmation}` -> 202 detail with durable pending state. Exact confirmation: `Stop this owned review; prior native effects and dispatched publications cannot be undone`. The UI first shows a keyboard-accessible explicit confirmation dialog naming that observed run/head. Only an owned running job without a prior request is actionable. A signal request is not completion; owned adapter shutdown must settle before recording `cancelled`/confirmed. Refusal or cleanup uncertainty stays `running`/unconfirmed and retains its concurrency slot and same-PR exclusion. Restart records interrupted/unconfirmed, not confirmed cancellation. No global termination or mode/model fallback is used by these actions.
- Invalid shapes use 400 `invalid_review_job_action`; missing explicit running confirmation uses 400 `review_confirmation_required`. Stale/foreign identities, double requests, already-finished runs or unavailable running ownership use 409 `review_job_conflict`. Reload GET state after a conflict or lost response instead of retrying against a different job.

Both accepted actions retain snapshots, immutable completed results, edited drafts, proposals, questions and all submission evidence. Already-completed work wins a finish/cancel race. Late results from an accepted running cancellation cannot create drafts/proposals. These actions advance the existing PR publication hold version/generation and require the existing explicit future-review re-enable flow; they change no settings, consent table or provider/tool grant. They cannot undo native effects or dispatched/uncertain external writes.

Stopped exact heads suppress automatic full-review re-enqueue, including same-SHA requests and commit triggers across restart. Explicit Review/Re-review remains available; pending exact-head dedup still applies. A different head remains eligible under existing policies. Eligible FIFO, concurrency and same-PR sequencing remain; Ask AI has no new controls. Native cancellation is owned process-group shutdown, not containment of detached malicious descendants. Docker retains its existing exact owned-container supervisor and cleanup proof. [Limits and inert evidence](docs/review-controls.md).

## Automatic submission and human-review overrides

This narrowly extends manual-only app publication with separately saved, default-off consent for **future automatic full reviews**. It does not activate existing polling or draft-review policies. AI verdicts, Connected, merge readiness and implementation approval grant no publication authority. Manual exact preview/confirmation remains available for every author, including while any automatic hold is active. The [automation guide](docs/automatic-submission.md) describes consent, same-pass detection and operational limits.

### Saved repository author/action policy

- `AppState.settings.autoSubmission?:AutoSubmissionPolicy` is `{repository,enabled,authors:[{username,actions:ReviewVerdict[]}],version,consentedAt}`. New installations and repository changes start Off, empty authors, version 0 and null consent. The backend implementation will always project it; absent fields in older clients/fixtures grant nothing. The publication version is independent of the four existing `AutomationPolicy` flags and draft save versions.
- `PATCH /api/settings/auto-submission`, body `AutoSubmissionUpdate -> AppState`, accepts exactly `{repository,expectedVersion,enabled,authors,confirmation?}`. Repository must match the currently configured nonempty repository. Send the whole table, not a partial action grant. Every enabled Save requires the exact shared `autoSubmissionConfirmation`: `Automatically publish untouched future automatic full-review drafts using these repository author/action permissions`. Off saves need no confirmation. The backend assigns the next durable version and consent time, never accepts caller-supplied times/provenance, and queues or publishes nothing. Every save invalidates earlier run publication provenance, including an unchanged enabled save. Disabling/removing permissions takes effect before awaited work can write. Changing repository revokes old authority and resets this policy; no policy follows an author into another repository.
- At most 100 author rows. `normalizeGithubUsername` trims and lowercases a 1-39 character GitHub login: ASCII letters/digits and single internal hyphens, no leading/trailing/consecutive hyphens, URL, `@`, whitespace or Unicode. Matching is case-insensitive **exact**, never substring/team identity. No live user lookup. `normalizeAutoSubmissionAuthors` rejects duplicate normalized usernames, duplicate/unknown actions, extra row fields and invalid rows as a whole, preserves row order and orders actions as `reviewVerdicts`. Empty tables and empty action arrays are valid. UI Add appends a row with **no actions**, and grants nothing until explicitly saved. Invalid bodies return 400 `invalid_auto_submission`; version/repository conflicts return 409 `auto_submission_conflict` without partial mutation.
- Actions authorize the **actual** verdict separately: COMMENT is a non-blocking review and is ineligible if the immutable result has any blocking finding, even one excluded from the draft. APPROVE approves the PR; REQUEST_CHANGES is the distinct stronger blocking-review authority. No permission relabels a verdict, drops a finding or changes the exact payload. An unchecked action stays unauthorized.

### Future provenance and edit intent

`ReviewRun.autoSubmission?:AutomaticReviewProvenance|null` records immutable `{outputContract:"1.1",repository,policyVersion,consentedAt,author,actions,trigger:"request"|"new_commits",prGeneration}` at automatic full-review enqueue. Manual/revision runs and historical runs without this capture are manual-only; nothing is backfilled. New policy consent must exist before enqueue. Only the latest successful full-review draft, untouched at version 1, from that exact future capture can qualify, on the current open PR head. Eligibility is rederived after every await against current consent, author/actions, PR generation, run success, latest draft id/version, competing jobs/submissions and all holds. A new head needs its own qualifying review; saving consent never publishes old, local, manual, revision or previously paused drafts.

`ReviewDraft.autoSubmission?:DraftAutoSubmission` contains `{provenance:AutomaticReviewProvenance|null,manualHold:{reason:"edit_intent"|"saved_edit"|"revision",at}|null}`. A missing field is manual-only. Immutable results and old edits remain unchanged.

- `POST /api/prs/:id/draft/edit-intent`, body `DraftEditIntent:{draftId,version} -> PullRequestDetail`, durably sets that draft's manual-only hold **before the editor permits typing or any editable finding/verdict mutation**. The UI must start read-only, request intent once on an explicit Begin editing action/focus attempt, and wait for a successful authoritative response before enabling editing. Client dirty state, an eventual Save, blur or optimistic local success is not authority. Failure leaves editing disabled with an actionable message. All draft-changing paths, including code-comment composers and included/severity/verdict controls, use this gate. Repeated matching intent is idempotent; stale versions or a matching automatic attempt still submitting/uncertain return 409 `draft_conflict`, unknown drafts 404. Confirmed previously submitted drafts remain editable and their earlier payloads remain immutable. Intent revokes remaining automatic authority, never cancels or undoes a dispatched remote write. Existing PUT Save and accepted revision also set the hold, so non-UI callers cannot bypass it. Discard/reload/restart never clears it. It affects this draft only and never blocks private drafting or manual preview/submit; there is no edit-hold clearing endpoint.

Canonical `ReviewResult` adds optional ingestion-compatible `humanReviewRequest:HumanReviewRequest|null`; generation `reviewSchema` requires it. ### Discussion, same-pass detection and durable holds

`DiscussionSnapshot` is pinned untrusted review input, not a public discussion browser: `{prId,headSha,fetchedAt,revision,coverage,sources}`. Capture it before generation with coverage and verified app-publication provenance and retain it separately from editable drafts. Existing refreshes acquire discussion for automatic reviewing or an existing same-pass observation; changed/unread versions mark detection unavailable without model calls. GET/SSE stays cached/inert. No reviewer-assignment or branch-protection inference.

Each `DiscussionSource` carries stable `{kind:"comment"|"review"|"inline_comment",id,version}`, author/type, exact body/permalink, updated time, thread/reply/review ids, resolved/outdated flags and `provenance:"participant"|"bot"|"app_automatic"|"unknown"`. `version` is a server digest of the exact source revision, including attribution/body/update/thread state; deleted sources cannot erase stored evidence. Known bots are excluded; any relevant human participant, including the PR author, counts by default. Own automated reviews/comments are excluded only from verified confirmed local review/comment identity and exact automated payload provenance, not from login, prose markers or a claim inside PR text. Unknown attribution/provenance cannot bind found evidence and makes unread detection unavailable. Thread replies retain conversation context.

`DiscussionCoverage` reports `complete` and `comments/reviews/threads:DiscussionPageCoverage:{pages,complete,error}`; threads includes every nested comments page. Exhausted pagination, cursor cycles, response/size limits, partial GraphQL errors, source drift and fetch failures are incomplete, never a fabricated empty discussion. Acquisition is bounded to 20 pages per collection (including nested thread pages), 1000 sources, 20000 UTF-8 bytes per source and 200000 aggregate input bytes including PR context. Overflow makes detection unavailable, never a clear decision or publication hold. `revision` binds head, PR context, all exact sources and coverage. Empty observations describe only supplied context; valid found evidence from partial coverage still holds.

Same-pass instructions consider explicit/contextual requests, relevant human participants including the author, quotations, negation, unrelated discussion and multilingual context. These are model judgments, not deterministic semantic guarantees. PR/discussion text is delimited **data**, never instructions, provider configuration or tool authority. Exact binding rejects quote/author/source/version/context/link/bot/app/unknown spoofs. Core-valid missing/malformed/unknown extension fields remain nonblocking unavailable, with no repair or model retry.

Independent classifier dispatch and its execution purpose/mode restrictions are retired. All supported review modes retain their configured tools, native boundaries and Main/Additional or skill orchestration, with no detection-only pass. Protection given up: authorized publication no longer waits for an independent, tool-disabled, complete and clear check. A missed request or unavailable discussion may allow publication. Dangerous tools remain unrestricted outside app controls.

`PullRequest.autoSubmission?:AutoSubmissionState` is separate from `PrStatus`: `{version,generation,status,message,draftId,evidence,check,detection?,failure?,reenableRequired}`. Status is `off|not_authorized|manual_only|eligible|human_review_requested|failed|uncertain|held|submitted`. `eligible` still requires fresh mechanical gates. `failure` is `{step:"publication"|"provenance"|"reconciliation",message,draftId,at}`; Inbox/detail name the failed step. `check:HumanReviewCheck|null` and classifier input/output types remain historical readers, not gates or execution purposes. A source-backed request shows amber hand **Human review requested**; unavailable detection is honest and nonblocking.

`HumanReviewEvidence` stores app-owned `{id,source,author,quote,url,detectedAt,acknowledgment:{action:"dismiss"|"resolve",at}|null}`. Evidence and genuine resume-required state persist across heads/restart/source deletion/edit/resolution/outdated status. Empty/unavailable observations never dismiss evidence or resume publication. Acknowledged identical source versions do not retrigger; new or changed source-backed requests pause again. Resolution/resume grants no action and clears no edit, uncertain-write or provenance hold.

- `POST /api/prs/:id/auto-submission/check` is retired (404), not redirected to inference or publication.
- `POST /api/prs/:id/auto-submission/reconcile {}` -> detail: conservative read-only exact uncertain-write/inline-provenance recovery. No model, write, retry or enqueue.
- `POST /api/prs/:id/auto-submission/acknowledge`, body `HumanReviewAcknowledgment:{expectedVersion,evidenceId,source,action:"dismiss"|"resolve"}` -> detail. No source is deleted.
- `POST /api/prs/:id/auto-submission/re-enable`, body `AutoSubmissionReenable:{expectedVersion,confirmation:autoSubmissionReenableConfirmation}` -> detail. Exact text: `Re-enable automatic submission for future automatic full reviews of this pull request`. Unresolved requests refuse with 409 `auto_submission_held`, stale state with 409 `auto_submission_conflict`. UI labels this Resume for later reviews. Mechanical failures remain separate. Success advances durable PR `generation`, affects only subsequently enqueued qualifying full reviews, and publishes/queues nothing. Holds accumulated on previously generated drafts do not become backlog authority.

### Exact payload, automatic deduplication and uncertain recovery

`SubmissionPreview.authority?` and `Submission.authority?` share `SubmissionAuthority`: manual, or automatic with exact repository/policyVersion/prGeneration/runId/draftId/draftVersion/headSha/discussionRevision. The backend alone creates it; absence is historical/manual, never inferred automatic consent. The manual preview/submit endpoints remain explicit user actions and cannot consume an automatic preview as a manual shortcut. There is no public automatic-submit endpoint. Internal automatic dispatch reuses the canonical preview placement/body construction and durable attempt-before-network-write path, preserving actual verdict, exact body/inline comments and private overview/evidence exclusion.

Immediately before any automatic attempt, freshly acquire writer/review inventory and head/diff, then recheck **all** authority/holds/latest-draft/save-version/job/submission state after every await and synchronously before recording the attempt and dispatching the write. Persist PR/head automatic dedup independently of preview ids. Any confirmed local submission, manual or automatic, suppresses further automatic publication on that head across restart; same-SHA re-requests cannot repost. Any uncertain or restart-stranded in-flight attempt pauses subsequent writes for the PR until conservative reconciliation. Never assume an exception means no write or blindly retry. Permission revocation during awaited work prevents dispatch. Human holds do not stop private reviews or explicit manual publication; competing/uncertain-write guards still apply.

Automatic recovery requires complete paginated remote review **and inline-comment** evidence: authenticated writer identity, actual event/state, exact commit, body and full canonical inline anchors/bodies, plus durable pre-write remote identity baseline and attempt timing. A body/commit-only match, a capped/incomplete list, wrong author/event/anchors, pre-existing identical review or multiple candidate matches is insufficient. Only one provably new exact matching review confirms the durable attempt; absent/ambiguous evidence remains uncertain and cannot grant retry authority. Equal/coarse timestamps cannot prove post-attempt ordering. New manual attempts retain the same recovery baseline and full-payload checks; historical uncertainty without one cannot fall back to body/commit-only matching. Confirmed automatic inline identities are durably retained only from a complete writer/full-payload match, so identical human copies are not excluded. No payload marker, extra GitHub comment or rewritten body is introduced for recovery. No restart or reconciliation automatically reruns inference or publication.

Final reads cannot prevent a comment, edit or push arriving after the last fetch and before GitHub accepts a review. App automatic/manual publication controls do not constrain unrestricted Dangerous native tools. Deterministic fixtures and browser acceptance are not live GitHub/provider/auth compatibility proof; implementation/tests must submit no real review.

The one-time migration advances existing PR generations, keeps consent/settings/history/edits/evidence/acknowledgments, removes only classifier-only pauses and preserves genuine resume requirements, provenance and uncertain-write holds. Enqueue's 1.1 marker plus generation fencing excludes every pre-change draft/job; no backlog or polling activation.

The UI retains `AutoSubmissionSettings` and `DraftEditGate`, and shows genuine evidence/resume, nonblocking unavailable detection, concrete failures and exact recovery in `AutoSubmissionCard`/`AutoSubmissionBadges`. Pending/failed intent never enables typing; unsaved/selected edits survive refreshes. Labeled web fixtures accept `autoSubmission=human|unavailable|off-hold` and `editIntent=locked|fail|slow|stale`. The [inert built-backend fixture](docs/automatic-submission.md#inert-acceptance-fixtures) exercises actual service/HTTP/database paths without real writes or inference.

## Model discovery

`POST /settings/models/discover`, body `HarnessModelDiscoveryRequest:{harness:"claude"|"codex"|"pi"}` -> `HarnessModelDiscovery`. This is an explicit read-only action, not automatic on startup, GET, SSE, field mount or harness change. No paths, models, commands, modes, permission or setup fields are accepted. Unknown harness/extra keys return 400 `invalid_model_discovery`; non-object/invalid JSON retains ordinary `invalid_body`/`invalid_json`. Existing origin/loopback and 1 MB body guards apply. GET on this path is 404. Source failures are structured **200** discovery results so retained custom IDs and source diagnostics remain usable. Responses have `Cache-Control: no-store`.

Types are shared in `shared/contracts.ts`:

- `HarnessModelDiscovery`: `{harness,checkedAt,status:"ready"|"partial"|"unsupported"|"error",availability:"not_checked",models:HarnessModelChoice[],sources:HarnessModelSource[]}`.
- `HarnessModelChoice`: `{model:string,label:string,sources:string[]}`. `model` is the exact opaque value for `reviewer.model` or `HarnessModelEntry.model`, not a display label. It uses the existing `validModel` validator. No null/default/custom sentinel is included in `models`.
- `HarnessModelSource`: `{id,kind:"configuration"|"cached_catalog"|"saved_selection"|"catalog",path:string|null,status:"ready"|"partial"|"missing"|"unsupported"|"error",modifiedAt:string|null,freshness:"unknown"|"not_applicable",message:string}`. Source IDs are `native-settings`, Pi-only `pi-models`/`pi-models-store`, `saved-selection`, and `native-catalog`. Paths are logical global source paths, never credentials or source bytes. `modifiedAt` is source file time, not a provider check. Cache/full-catalog freshness is always unknown.

`ready` means choices were acquired without source failure or omitted identifiers; Claude/Codex additionally require successful native catalog metadata. It does **not** mean a complete account catalog, authentication, access, mode compatibility or execution readiness. `partial` means a source failed but choices remain, identifiers were omitted by existing validation, or Claude/Codex catalog acquisition is unavailable beside retained configured/saved IDs. `error` means a source failed and no choices remain. `unsupported` means there are no choices and no source failure (for example missing executable and native files). Missing files/executables are distinct from read/protocol errors. Error messages never echo parser errors, stderr or config contents. No stale server-side fallback is used.

Discovery retains supported fixed global configuration fields and saved Main/Additional IDs. Pi's static declarations/offline catalog reads are unchanged and start no process. Claude/Codex additionally acquire the installed first-party catalog through credential-free native metadata: Claude `--bare` initialization (no prompt), Codex app-server `initialize`/`initialized`/paginated `model/list` (no thread or turn). Only PATH is inherited; homes, cwd, native config roots and temporary storage are disposable, with no native user config/auth copied. The existing command supervisor bounds each process to 15 seconds plus termination grace; protocol output is bounded to 5 MB, 2000 entries and 20 continuation cursors. Catalog source `native-catalog` is `kind:"catalog"`, with no path/file time and unknown freshness. Detected alternate-provider/profile/catalog overrides or unreadable config report unsupported instead of substituting a first-party catalog. Missing/incompatible native mechanisms remain visible and never turn configured echoes into discovery. No review entry capture, null resolution, Save, change event, catalog persistence, Docker action, authentication test, tool approval or work enqueue occurs. Full support matrix and native evidence: [model-discovery.md](docs/model-discovery.md).

Typed example (`satisfies HarnessModelDiscovery`), with illustrative timestamp/path/message text:

```ts

  harness: "codex",

      model: "fixture-codex-native",
```

With a malformed Codex source, the same saved custom choice remains: `status:"partial"`, only `fixture-custom-one` in `models`, `native-settings.status:"error"`, `modifiedAt:null` and a bounded source error message. With no saved choice it becomes `status:"error",models:[]`. With no source file, `native-settings.status:"missing"` does not prevent native catalog acquisition. If the executable is also missing, use `status:"unsupported",models:[]`. These are not transport errors and never replace a field's value. UI guidance: explicit Discover/Refresh only; show loading locally, source/error/unsupported details, discovery timestamp and possibly stale cache wording. Distinguish catalog entries (a contributing `catalog` or `cached_catalog` source) from configured/saved-only IDs, both per option and in the summary counts. Keep **Native default (resolved on Save)** as null and offer **Custom** unless the current value already is a listed choice. Opening shows all choices for that harness; typing after opening filters by id or label. Preserve saved and unsaved custom IDs even when absent from results; the response includes saved IDs but unsaved values remain client-owned. Share discovery by harness without sharing/overwriting row selection, collapsing repeated Additional entries or changing their IDs. Ignore obsolete responses after a harness switch. A retained previous response after transport/refresh failure must be labeled previous/stale with its own timestamp, never silently called successful. Membership is not a Save allowlist: existing model validation, Save-time default resolution, restricted-provider rules and Dangerous confirmation remain unchanged. Implemented by `web/src/components/ModelSelect.tsx` inside the Execution card for Main, every Additional row and the Docker/Dangerous model field; browser evidence is in [model-discovery.md](docs/model-discovery.md#searchable-selectors).

## Host-owned MCP OAuth: backend handoff

## Import and sync lifecycle

`GET /api/state` and every other `AppState` response include required `operations: {sync: SyncOperation | null, imports: ImportOperation[]}`. These are service-owned, memory-only projections of `ReviewService.sync` and `importPullRequest`, not browser request flags, persisted jobs or progress estimates. `shared/contracts.ts` defines the types:

- Both carry `id` (opaque operation UUID), `repository` (captured at start), `status: "running" | "completed" | "failed"`, `startedAt` (ISO timestamp), `finishedAt` (null while running, actual settlement timestamp otherwise) and `error` (null except for a failed operation's message).
- `SyncOperation` also carries `mode: "manual" | "scheduled"`. `sync` is null before the first accepted sync in this service instance; otherwise it is the current or latest sync. Concurrent manual/scheduled calls join the existing promise and identity, retaining the first call's mode and query scope. A missing repository is refused with 400 `repository_required` without changing operation state. A scheduled call with no eligible work leaves it unchanged.
- `ImportOperation` also carries `prId` and `number`. `imports` holds the current or latest operation for each explicitly attempted PR identity in this service instance, including retained failures. Identity uses the existing URL parser's exact repository string and numeric PR number, not the raw URL (query/fragment/trailing slash do not distinguish it). After ordinary URL/repository validation, simultaneous imports of the same identity share the entire fetch/observe/readiness promise and result or error. Sequential imports still refresh again with a new operation id and replace that identity's prior outcome. Different PR imports and a sync can overlap; each remains running until its own work settles. No global import/sync serialization or query expansion is introduced. This coalescing is in-flight only, not a cache or a review deduplication policy.

Start and final settlement emit existing `change` invalidations (`{}` for sync, `{prId}` for import), in addition to existing data invalidations. The operation remains running through metadata/diff work, observation and existing freshness/readiness work, then settles even when the initiating HTTP client disconnects. Import retains existing open-only/refusal and provenance semantics: invalid URL, repository mismatch or malformed HTTP body start nothing and do not replace another operation; an accepted fetch that fails or returns a closed/merged PR settles failed. The pre-existing empty-repository initialization remains, including when a later fetch fails. A best-effort readiness lookup that records unknown without rejecting the import/sync does not falsely turn the whole operation into a failure. Review jobs that existing enabled automation may enqueue are separate and are not included in this lifetime; no policy is enabled by these fields.

POST response shapes/status behavior is unchanged: sync returns `AppState` (including on upstream failure, via its existing HTTP 200 plus `health.pollError` behavior), while import returns `PullRequestDetail` or its existing HTTP error. Consumers must check `operations.sync.status`, not treat HTTP 200 alone as sync success. Import completion/failure after refresh is available in the next `AppState`, even though no import response survived. Retained outcomes stay until the next operation for that scope or backend restart; there is no expiry timer, acknowledgement endpoint or completed-operation log. Entries can describe a previously configured repository and must not be relabeled as work for the current one.

Fresh load and SSE reconnect must read authoritative state; SSE is invalidation, not an event history (each connection starts with `change {}`). Lost transport is not proof that work stopped: re-fetch on reconnection rather than persisting/clearing a browser spinner as authority or replaying the POST. A service restart begins with `{sync:null,imports:[]}` and never restores active bits or retries lost work; these fields make no crash-success claim. Stored PRs, sync health metadata, settings, drafts and review history retain their existing persistence rules. There are no progress counts, percentages, cancellation, provider calls on GET or new routes. PR-detail freshness checks, pre-review refreshes and preview refreshes are not global sync/import operations.

Backend tests, the reusable delayed inert shipped-browser recipe and the inbox UI consumer are described in [sync-lifecycle.md](docs/sync-lifecycle.md). The typed web mock tracks these operation semantics with explicit test gates.

## Review API

- POST /api/sync body {} -> AppState. Perform a bounded refresh of the eligible set, do not hold for AI reviews. Discovery reads the repository's open pull request list as a compact projection (number plus requested reviewer logins and team ids), resolves the user's organization team membership once, and fetches full details and diffs only for pull requests addressed to the user or one of their teams plus every currently tracked eligible pull request, so unrelated pull requests are neither imported nor diffed. Tracked pull requests that closed or merged, or lost their request without an explicit import or successful review/submission history, are refreshed and retired from the inbox without deleting their history. It records observed heads and request events as baselines; it queues a review only where the PR's effective automation policy is on and armed. With every policy off it refreshes metadata only. Individual manual review/revision actions remain available. Report failures explicitly. No unbounded polling request.
- PATCH /api/prs/:id/automation body Partial<AutomationOverrides> -> PullRequestDetail. Only reviewNewCommits and reviewRequests can be overridden, each as "inherit", "on", or "off"; polling is global only, so pollCommits and pollRequests keys are ignored and stored legacy per-PR polling overrides are dropped at startup with no runtime effect. `pr.automation` returns the two stored overrides and `pr.effectiveAutomation` the resolved result: polling flags mirror the global settings and an auto-review flag is on only when its global polling switch is on and the override (or, for inherit, the global default) is on. A PR cannot opt into polling while the global switch is off.
- POST /api/prs/import body { url: string } -> PullRequestDetail. Import an explicit GitHub PR URL for manual review; require its repository to match the configured repository or use it to configure an empty installation. A successful import durably marks the pull request `imported`, including one that is already tracked or currently requested, and that mark survives refreshes, polls, and request removal. A closed or merged pull request is refused with 409 `pr_closed` and nothing is stored, though an already known one still has its state refreshed. Import alone need not launch AI.
- GET /api/prs/:id -> PullRequestDetail. `drafts` lists every draft newest first (by review run creation, or by draft creation for a local draft with `runId` null), `draft` is the latest one (the default when a PR opens), `questions` lists every question oldest first with its pinned selection, status, answer, and error, and `freshness` is the last saved check against the latest draft, or null when nothing has been reviewed yet. A migrated legacy draft whose `runId` still names a revision run (its originating full review could not be resolved) is listed after every full-review draft and is never the latest.
- POST /api/prs/:id/check body {} -> PullRequestDetail. Metadata-only freshness check: re-fetch the PR and diff, then compare the displayed review baseline (the draft's head, else the latest completed review run's head) against the current head using exact SHAs. `freshness.status` is fresh, stale (with the new commits, bounded and flagged `truncated`), rewritten (diverged history such as a force-push, listing the commits on the new head), unavailable (GitHub returned 404 for the comparison, for example when the baseline is gone), or unknown. A GitHub failure keeps the last known status and commits and sets `error`; it never clears a stale warning. It never consumes request events. A head change observed here queues a review only when the PR's effective reviewNewCommits policy is on. The UI calls this once when a PR opens; periodic checks are owned by the backend poll while commit polling is on globally, so the browser runs no interval of its own.
- GET /api/backlog -> `BacklogReviewPreview:{limit:5,entries:Array<{prId,number,title,headSha,reason:BacklogReviewReason|null}>}`. Local read-only selection over this repository's open tracked inbox, sorted by number. Null reason is eligible; exclusions are `reviewed_head`, `automation_off` or `busy`. Eligibility uses completed full-review history of the exact head, not visual status/drafts/revisions, and effective commit automation or current-request automation. Any queued/running review or revision, or an in-flight backlog refresh, is busy. No sync, capture, arming or queueing on GET.
- POST /api/backlog body `BacklogReviewRequest:{selections:Array<{prId,headSha}>}` -> 200 `BacklogReviewOutcome[]:{prId,status:"queued"|"skipped"|"busy"|"error",message,runId:string|null}`. Accept only 1-5 distinct exact observed selections, no extra fields; malformed/unbounded bodies return400 `invalid_backlog`. Refresh only selected PRs using the request-aware scoped GitHub adapter, preserve commit/request arming, then synchronously recheck repository/inbox/policy/history/pending work and exact selected head. Report `not_tracked`, `reviewed_head`, `automation_off`, `busy` or `head_changed` skips; refreshed failures and unsupported capture are per-selection errors, not cached-code review or automatic retry. Queue through the existing full-review queue with `manual` trigger and null automatic-submission provenance, even with all publication permissions on. No new scheduler or database migration. Normal concurrency, per-PR sequencing, immutable captures, restart persistence and edited-draft preservation apply. Manual publishing and future automatic triggers are unchanged. See [bounded catch-up semantics](docs/reviewing.md#bounded-backlog-catch-up).
- POST /api/prs/:id/review body {} -> PullRequestDetail. Re-fetch the PR metadata and diff first, then queue a manual review whose immutable snapshot is that exact head, base, and diff; do not hold the request until the selected review finishes. A refresh failure returns 502 `refresh_failed` and a closed or merged PR returns 409 `pr_closed`; neither reviews cached code. Repeated clicks while a manual job for the same head is pending do not spawn duplicate jobs; a pending job for an older head is not passed off as the new one.
- PUT /api/prs/:id/draft body DraftUpdate -> PullRequestDetail. Persist validated edits to the draft named by `draftId` using that draft's version concurrency check. DraftUpdate carries `body`, `findings`, and `verdict` only; the draft's `overview` is read-only private context that a save never changes, and `body` is posted verbatim as the review body. A finding has `side` (RIGHT for the new side, LEFT for the old side), `line`, and `startLine` (null for a single line; otherwise less than `line`, both on the same side); `startLine` without a line, or not below it, is rejected as `invalid_finding`. Finding `evidence` is read-only: the stored evidence is kept for existing finding ids; a new finding whose `questionId` names a completed draft-comment question of this PR at the draft's head gets that question's evidence, and every other new finding gets empty evidence. PR status and counts change only when the edited draft is the latest one.
- Every successful full review creates its own draft (version 1) from its immutable result; there is no adopt step. The latest draft is the one whose review run (or, for a local draft, the draft itself) was created most recently, independent of completion order or edits.
- POST /api/prs/:id/drafts body {} -> 201 PullRequestDetail. Create a local draft for the PR's current head: `runId` null, version 1, empty overview and body, no findings, verdict COMMENT. It never creates a run, never sets `lastReviewedAt`, and is idempotent per head (an existing local draft for that head is returned unchanged). It counts as a draft for status, counts, Outdated, preview and submit; `revise` on it fails with 409 `snapshot_missing` because there is no review snapshot.
- POST /api/prs/:id/questions body QuestionRequest -> 202 PullRequestDetail. Queue a question about a code selection: `mode` is explain, investigate, or draft_comment; `range` names one file with `from`/`to` line refs (`side` LEFT or RIGHT and a line number, resolved against rows of the stored diff) and the `baseSha`/`headSha` the diff was shown at; optional `question` (at most 4000 characters), `parentId` (an earlier question on the same head, whose turns become prior context), and `draftId` (read-only context, must exist). A head or base that differs from the PR's current one is 409 `head_mismatch`; a range that does not resolve in the stored diff is 400 `invalid_selection`; more than five queued questions is 429 `too_many_questions`. The stored `selection` carries the resolved snippet, rename source, hunk spanning, and per-side anchor projections. Questions run one at a time in their own lane, never behind a review.
- POST /api/prs/:id/questions/:qid/cancel body {} -> PullRequestDetail. A queued question becomes cancelled immediately; a running one is aborted (only its own process tree) and becomes cancelled; anything else is 409 `question_finished`.
- POST /api/prs/:id/questions/:qid/retry body {} -> 202 PullRequestDetail. Re-queue a failed, cancelled, or interrupted question with the same pinned context; an active one is 409 `question_active`. Restart marks queued and running questions interrupted; nothing reruns automatically.
- POST /api/prs/:id/revise body RevisionRequest -> PullRequestDetail. Queue an AI revision against the exact `draftId` and `draftVersion`, using that draft's own review snapshot. Successful output becomes a pending RevisionProposal bound to that draft. Empty findingIds or omitted means whole draft.
- POST /api/prs/:id/proposals/:proposalId/apply body { expectedVersion: number } -> PullRequestDetail. Accept only against the proposal's own draft at its matching source version. Conflicting proposals need regeneration, not silent overwrite.
- POST /api/prs/:id/proposals/:proposalId/reject body {} -> PullRequestDetail.
- POST /api/prs/:id/preview body { draftId: string, draftVersion: number } -> SubmissionPreview. Re-fetch PR revision and diff anchors, reject outdated drafts, and save the exact outgoing payload for that draft. The payload body is the draft's `body` followed by body-only findings; the overview and evidence are never included. A finding is anchored inline when its `line` exists on its `side` inside a hunk of the current diff (new side: added or context rows; old side: removed or context rows) and, for a range, its `startLine` is in the same hunk on that side; the comment then carries `side`, `line`, and for ranges `start_line` and `start_side`. Findings whose lines are not in the diff on that side, that cross hunks, that sit on headers or metadata, or that have no path go in the body once, prefixed with `path:line` or `path:start-line`, plus `(old)` for old-side anchors. Skip excluded findings. Every posted finding text starts with **Blocking.** or **Non-blocking.** exactly once, taken from the finding's selected severity: a recognized leading severity label in the saved body (bold or plain, `.` or `:`) is replaced, the rest of the saved body is kept verbatim, pre-existing findings are marked once, and the private evidence field is never included. Saved drafts are not modified.
- POST /api/prs/:id/submit body { previewId: string } -> Submission. This manual endpoint is only callable by the explicit confirmation button; the narrowly consented internal automatic path is described above. Revalidate current draft, PR state, head revision, and saved preview. Record an in-flight attempt durably before any network write. Never automatically retry an ambiguous write; reconcile GitHub review identity/payload first.
- GET /api/events -> server-sent events named change, JSON data { prId?: string }. UI refreshes state/detail on change, handles disconnects, and debounces bursts. Keep a heartbeat and tear down connections on shutdown. Run progress updates arrive as ordinary change events for the run's PR, throttled by the backend.

`PullRequest.imported` is true only for pull requests the user explicitly imported by URL through this endpoint; it is never inferred from reviews, drafts, or earlier broad polls, and databases from before it existed start with it false everywhere. `PullRequest.requestSource` records who the current review request is addressed to: `direct` (the authenticated user), `team` (only a team the user belongs to in the repository's organization), `both`, or `unknown` for a row stored before provenance existed and not yet re-synced; it is null whenever `requested` is false. Current request fields are set by request polls and manual sync, preserved by commit-only polls, freshness checks and review refreshes, and cleared when the request disappears or the pull request closes. `PullRequest.createdAt` is GitHub's creation time, null only for rows imported before it was stored and not refreshed since; refreshes fill it without clearing known creation time.

`PullRequest.historicalRequestSource` is required and is `direct`, `team`, `both` or null. The existing PR row stores the union of genuine typed requests observed locally, independently of the current request flag, imports and review success. It survives request removal, all refresh paths, new heads, closure and restart. On upgrade, `historical_request_source` is backfilled only from typed current requests and immutable `run_snapshots` whose captured PR recorded `requested: true` with known `requestSource`. Multiple personal/team observations combine to `both`. Completed reviews/submissions alone, imports, untyped request events and author membership never establish it; already-erased types without a qualifying capture stay unknown, with no live or historical GitHub fetch by the migration. Snapshots, runs, drafts and automation are unchanged.

The inbox groups on known historical or current request provenance: any direct request wins Requested of you, otherwise a team request wins Requested of your teams, and the rest use Other tracked PRs. Each PR appears once, including when personal and team requests were observed separately. This changes grouping only: `inboxEligible` still requires OPEN plus a current request, explicit import or successful full-review/confirmed-submission history. Closed/merged removal and unreviewed/unimported removed-request exclusion remain unchanged; a retained reopened PR returns to its historical group. Ordering stays Ready first, then by `requestedAt` (requested groups, falling back to creation time when no request time is known) or `createdAt` (Other) ascending, never by `updatedAt`.

`PullRequest.mergeReadiness` is GitHub's own merge readiness for the exact recorded head, or null for a row never checked (including every row of a database from before it existed). It is read with one GraphQL query (`mergeStateStatus`, `mergeable`, `reviewDecision`, `isDraft`, `isInMergeQueue`, and the latest commit's `statusCheckRollup` contexts with `isRequired`) on the same paths that refresh the pull request: manual sync, scheduled polls, import, the freshness check, and the refresh before a review or preview. GET /api/state and GET /api/prs/:id never call GitHub for it. `state` is `ready` only when GitHub reports `CLEAN` or `HAS_HOOKS` for `headSha`; `unstable` when GitHub allows the merge but non-required checks are failing or pending; `blocked` for `BLOCKED`, `BEHIND`, `DIRTY`, and `DRAFT`; `queued` while the pull request is in a merge queue; and `unknown` while GitHub is still computing, when the answer was for another head, or when the lookup failed. `blockers` lists every reason GitHub exposes, in order: draft, merge conflicts, behind the base branch, the current `reviewDecision` (`changes_requested` or `review_required`, so a null decision is never treated as a missing review and dismissed or superseded reviews never count), then failed and pending checks split into required and non-required counts with names in `detail` and a link to the check or the checks tab. A reason is `required: false` when GitHub does not enforce it (an optional check, or a review decision on a mergeable pull request). A `BLOCKED` pull request with no exposed cause carries one generic `blocked` reason linking to the pull request. `checksTruncated` flags that GitHub returned only the first 100 of more check contexts, so the counts are lower bounds. `state` is `ready` only when that evidence is coherent and complete: GitHub's `state` is `OPEN`, `headRefOid` and the latest commit are `headSha`, the response carries no GraphQL `errors`, `mergeable` is not `UNKNOWN`, the check list is not truncated, and no draft flag, conflict, or failing or pending check marked required contradicts the `CLEAN`/`HAS_HOOKS` (or, for `unstable`, `UNSTABLE`) status; any of those instead yields `unknown` with the reason in `error` and only the blockers GitHub actually exposed, with required checks still labeled required. A lookup failure records an `unknown` snapshot for the current head whose `checkedAt` is the time of the failed attempt and whose `error` is the failure; the previous same-head result, when it had a known state, is carried in `lastKnown` (`checkedAt`, `state`, `mergeStateStatus`, `blockers`, `checksTruncated`, the time being when it was actually observed) so the UI can label it as last known, and it is cleared by the next known answer. `lastKnown` is null on every snapshot whose `state` is not `unknown`, when the head moved, and for databases from before it existed. When the head moved during a failure, the stale snapshot is replaced by an `unknown` one for the new head with the error. The snapshot is bound to `headSha` and `checkedAt`; a snapshot whose head differs from `pr.headSha` is displayed as stale, never as ready. Readiness is observation only: it grants no merge permission, never merges, reviews, or approves, and closed or merged pull requests are not re-checked.

`PullRequest.hasReviewHistory` is a required boolean derived on read from any stored full review run (`kind: review`, `status: completed`, non-null `result`) or confirmed local submission (`status: submitted`) for this PR, on any head. Open PRs with this evidence remain in the inbox and the existing refresh/polling scope after request removal, including across restarts and new commits, until closed or merged. No new database column, migration, import provenance or automation setting is introduced. Page visits, local drafts alone, revisions, unsuccessful runs and unrelated legacy fetched rows do not qualify; retained history and manual edits are unchanged.

`PullRequest.viewerApproval?: {viewerLogin:string,headSha:string,commitSha:string}|null` is an additive inbox/detail projection of the authenticated viewer's latest non-pending GitHub review, including reviews made outside this app. Only an `APPROVED` review with a known exact commit produces a value. Completed reviews are ordered by submission time, then GitHub review id; later `COMMENTED`, `CHANGES_REQUESTED` or `DISMISSED` reviews supersede approval, while `PENDING` drafts do not. `headSha` binds the observation to the fetched PR head and `commitSha` names the approved commit. Equal commits display **Approved by you**; a known different commit displays **Approved by you at an earlier revision**, never a current approval. Missing viewer, unsupported/incomplete fields, incomplete pagination or acquisition failure return null. Unknown must not display approval. Neither Submitted status nor local submission receipts establish it.

Acquisition reuses the existing bounded complete review paginator and review response type on ordinary full PR refreshes, with polling's already fetched viewer login reused. It reads no inline comments or unrelated discussion and starts no extra poll, review, classifier or write. A nullable `prs.viewer_approval_json` column starts empty without historical backfill; projections survive restart only for the authenticated matching viewer and observed head. Unknown refreshes replace positive values, failed PR refreshes/polls clear affected cached positives, and a head mismatch suppresses them. This display-only field changes no draft, publication gate, automation setting, merge readiness or review output contract.

`PullRequest.hasReviewedHead` is a required boolean in inbox state and detail responses. It is true exactly when this PR has any stored full review run (`kind: review`, `status: completed`, non-null `result`) whose `headSha` exactly equals the PR's current `headSha`. It is derived from immutable runs on read, including after restart, with no new database column or migration. Old-head reviews, AI revisions, queued/running/failed/interrupted runs, local or edited drafts, display status, and `lastReviewedAt` cannot establish it; later unsuccessful runs or revisions cannot erase an earlier matching success. It reports local review history only and changes no review, automation, draft, or submission guards.

`ReviewRun.progress` is the run's recorded stages and harness activity, or null for runs stored before it existed (their stage timing is unavailable, never reconstructed). `phases` lists, in the order they started, the app phases actually performed: `sync` (only on manual reviews, recorded from the refresh that preceded the snapshot, so its timestamps precede `createdAt`), `checkout`, `codex`, `claude` (archived fixed-pipeline phases only), `workflow` (current Isolated, Docker or Dangerous execution), and `finalize`, each with `status` (`running`, `completed`, `failed`, `skipped`, `interrupted`), `startedAt`, `finishedAt`, and a clamped `detail`. A revision run never has `sync`. `activity` is the bounded tail (at most 40) of sanitized labels observed from the app and the Claude Code and Codex event streams, each with `at`, `source` (`app`, `codex`, `claude`), `kind` (`phase`, `read`, `search`, `list`, `command`, `tool`, `message`), and `label` (flattened, at most 120 characters); `activityCount` is the total observed, `lastActivityAt` the time of the newest one, and `updatedAt` the last persisted write. A label is a fixed operation phrase plus at most one path, shown relative to the owned checkout only when it resolves inside it and otherwise as `a file outside the checkout`. Labels and failed-phase `detail` values never carry prompts, model text or reasoning, tool results, file contents, command lines or arguments, environment assignments, search or glob patterns, command output, or raw error payloads; the full failure diagnostic is only in `error` and the log. Progress is persisted and emitted on the change stream at most every 750ms per run, immediately on phase changes. Only a run whose `status` is `running` can have a phase whose status is `running`; restart marks such phases `interrupted` and a failure marks the current phase `failed` with the error. No field estimates remaining time or completion.
